7. PLAYLIST ORCHESTRATION
======================================================================

Pseudo-flow:

load current item
validate mapping
load media
load timeline
play
while running:
  update clocks
  dispatch events
on media end:
  mark item completed
  next enabled item
if no next item and loop:
  current_index = first enabled
  increment loop_count
  continue session_clock
else:
  completed

JSON timeline được đánh giá theo Video Clock.
Session Clock chỉ tích lũy và không dùng trực tiếp để so event time của file JSON.

8. TIMELINE SCHEDULER CONTRACT
======================================================================

Input:
- Video Clock.
- Timeline events.
- Current event states.
- Bridge status.
- Active product state.

Dispatch rule:
- Event pending.
- video_time_ms >= event.time_ms.
- Event chưa expired.
- Event không conflict.
- Bridge connected.

Nếu Bridge disconnected:
- Event chuyển waiting_bridge hoặc giữ pending nội bộ.
- Queue giới hạn.
- valid_for_ms quyết định expiry.

Sau reconnect:
- Chọn event mới nhất còn valid.
- Event cũ expired/skipped.
- Không replay toàn bộ backlog.

Seek:
- Forward seek: bỏ qua event trước vị trí mới theo policy.
- Backward seek: event acknowledged không reset mặc định.
- Scheduler phải idempotent.

9. WEBSOCKET BRIDGE PROTOCOL
======================================================================

Endpoint:
ws://127.0.0.1:<configured_port>

Handshake:
{
  "protocol_version": "1.0",
  "type": "HELLO",
  "extension_version": "1.0.0",
  "pairing_token": "...",
  "tab_context": {
    "url": "...",
    "title": "..."
  }
}

Server response:
{
  "protocol_version": "1.0",
  "type": "WELCOME",
  "connection_id": "...",
  "heartbeat_interval_ms": 5000
}

Command:
{
  "protocol_version": "1.0",
  "message_id": "msg_...",
  "session_id": "session_...",
  "type": "PIN_PRODUCT",
  "created_at_ms": 0,
  "expires_at_ms": 0,
  "payload": {
    "product_id": "..."
  }
}

Ack:
{
  "protocol_version": "1.0",
  "message_id": "msg_...",
  "type": "COMMAND_RESULT",
  "status": "SUCCESS",
  "executed_at_ms": 0,
  "payload": {
    "product_id": "..."
  },
  "error": null
}

Status values:
- SUCCESS
- FAILED
- EXPIRED
- TAB_NOT_READY
- PRODUCT_NOT_FOUND
- NOT_PAIRED
- INVALID_COMMAND

Requirements:
- message_id idempotent.
- Max message size.
- Heartbeat.
- Timeout.
- Reconnect backoff.
- Localhost only.
- Pairing token rotate được.

- Source.

- Tests.
- Signing workflow.
- Release automation.

- Releases.

- installer/package.

Build flow:

private main/tag
  -> CI test
  -> build artifact
  -> sign
  -> generate checksum
  -> publish public release
  -> generate and publish latest.yml

Client flow:

launcher
  -> Splash Gatekeeper fetches latest.yml
  -> compare semver
  -> mandatory?
  -> download staging
  -> verify SHA-256
  -> verify signature
  -> close app
  -> install
  -> health check
  -> restart

Atomicity:
- Không overwrite file đang chạy.
- Updater process độc lập.
- Backup previous version.
- Marker file update_in_progress.

15. SPLASH GATEKEEPER ARCHITECTURE
======================================================================

Process model:

DTAAutoLiveLauncher.exe
  |
  +-- SplashWindow (visible)
  |
  +-- UpdateCheckService
  |     |
  |     +-- fetch latest.yml
  |     +-- parse version
  |     +-- compare local version
  |
  +-- if up-to-date -> start/show MainApp.exe
  |
  +-- if update -> launch DTAUpdater.exe
        |
        +-- download package
        +-- verify checksum/signature
        +-- stop old processes
        +-- backup current version
        +-- install/replace
        +-- health check
        +-- restart launcher
        +-- rollback on failure

MainApp.exe không được show window trước khi Launcher cấp quyền.

Splash UI states:
- INITIALIZING
- CHECKING
- UPDATE_AVAILABLE
- DOWNLOADING
- VERIFYING
- INSTALLING
- RESTARTING
- UP_TO_DATE
- NETWORK_ERROR
- UPDATE_ERROR

Event contract:
- status_changed(message)
- progress_changed(percent, downloaded_bytes, total_bytes)
- update_available(version)
- up_to_date(version)
- retry_allowed
- fatal_error(code, message)

16. LATEST.YML CONTRACT
======================================================================

Canonical keys:

version: 1.0.1
files:
  - url: DTA-AutoLive-Setup-1.0.1.exe
    sha512: BASE64_SHA512
    size: 123456789
path: DTA-AutoLive-Setup-1.0.1.exe
sha512: BASE64_SHA512
releaseDate: 2026-07-27T00:00:00.000Z
releaseNotes: |
  Release notes.

DTA AutoLive có thể bổ sung key riêng dưới namespace dta:
dta:
  mandatory: true
  minimumSupportedVersion: 1.0.0
  channel: stable

Quy tắc tương thích:
- Các key canonical phải giữ tên.
- Extension key không được làm parser cũ lỗi.
- Checksum SHA-512 của latest.yml là chuẩn chính để tương thích hệ cũ.
- Có thể phát hành thêm SHA-256 phụ, nhưng không thay thế SHA-512 nếu workflow cũ phụ thuộc nó.

17. GITHUB ACTIONS RELEASE CONTRACT
======================================================================

Trigger:
on:
  push:
    tags:
      - 'v*'

Private Repo workflow:
1. checkout
2. setup Python
3. install locked dependencies
4. lint/type/test
5. build Windows installer
6. calculate SHA-512
7. generate latest.yml
8. publish installer + latest.yml to Public Repo release
9. verify public download

Secret:
- DTA_RELEASE_TOKEN
- Chỉ cấp quyền ghi release vào Public Repo.
- Không đưa vào binary, logs hoặc artifacts.

Khác với ví dụ Electron cũ:
- Không dùng electron-builder.
- Dùng script build Python tương ứng, ví dụ PyInstaller/Nuitka + Inno Setup/NSIS.
- Tuy nhiên Git Tag trigger, DTA_RELEASE_TOKEN, Public Repo và latest.yml phải giữ nguyên.

======================================================================
18. STRICT MODE NETWORK POLICY
======================================================================

Default:
strict_update_check = true

Nếu network error:
- Splash giữ mở.
- MainApp không start.
- Retry và Exit là hai action duy nhất.
- Retry có backoff và timeout.
- Error log không chứa token.
- Không dùng cached latest.yml để bỏ qua check trong v1.0, trừ khi sau này có ADR phê duyệt offline grace period.
